# Архитектура проекта

Подробное описание архитектуры сервиса сокращения ссылок.

## Обзор

Проект построен по принципам **Чистой Архитектуры** (Clean Architecture) и **Domain-Driven Design**. Код разделён на четыре основных слоя, каждый из которых имеет чёткие границы ответственности.

### Создание короткой ссылки

```
┌────────┐     ┌────────────────┐     ┌────────────┐     ┌──────────────────┐
│ Клиент │────>│ API Controller │────>│ LinkService│────>│CreateShortLinkUC │
└────────┘     └────────────────┘     └────────────┘     └────────┬─────────┘
                                                                  │
                        ┌─────────────────────────────────────────┤
                        │                                         │
                        ▼                                         ▼
              ┌──────────────────┐                     ┌──────────────────┐
              │  HashCalculator  │                     │  CodeGenerator   │
              │  hash(url)       │                     │  generate()      │
              └──────────────────┘                     └──────────────────┘
                        │                                         │
                        ▼                                         │
              ┌────────────────────┐                   ┌────────┴───────────┐
              │   Cache (L1+L2)    │                   │     PostgreSQL     │
              │ get_by_hash(scope) │                   │find_live_by_hash() │
              │ save()             │                   │ save()             │
              └────────────────────┘                   └────────────────────┘
                        │                                         │
                        └────────────────┬────────────────────────┘
                                         │
                                         ▼
                               ┌──────────────────┐
                               │ ShortLinkResponse │
                               │ 201 Created       │
                               └──────────────────┘
```

**Дедупликация — в пределах владельца и только по живым ссылкам.**
Ключ — пара «хэш URL + владелец»: зарегистрированный пользователь сам себе
область, гость — в пределах своего `guest_identifier`, ссылки без того и
другого (созданные из CLI) — в общей анонимной области. Истёкшие ссылки в
дедупликации не участвуют: иначе повторное сокращение отдавало бы мёртвый
код, а рабочую ссылку на этот URL нельзя было бы создать уже никогда.

Отсюда два следствия:

- уникальный индекс `urls.url_hash` снят (миграция `0003`) — один и тот же
  URL законно встречается у разных владельцев, а после истечения — и у
  одного и того же;
- попадание в кэш по хэшу — это заявка, а не ответ: код сверяется с БД,
  прежде чем быть отданным как существующий. Ключи `code:` и `hash:`
  вытесняются независимо (`allkeys-lru`), поэтому запись в кэше переживает
  строку, о которой рассказывает.

## Ключевые компоненты

### Domain Layer (Слой домена)

Содержит бизнес-логику, не зависящую от инфраструктуры.

- **Сущности**: `Link`, `User`, `Role`, `Permission` — неизменяемые данные с поведением
  - `Role` — frozen dataclass с иммутабельным `tuple[Permission, ...]`
  - `User` — identity-based `__eq__` и `__hash__` на основе ID
- **Объекты-значения**: `OriginalUrl`, `ShortCode`, `UrlHash`, `Email`, `OwnerID` — валидированные параметры
  - Все validation ошибки бросают `ValidationError(DomainError)` вместо `ValueError`
- **Интерфейсы репозиториев**: `LinkRepository`, `UserRepository` — абстракции хранения
- **Политики**: `HashCalculator`, `CodeGenerator` — алгоритмы, передаваемые как зависимости

### Application Layer (Слой приложения)

Оркестрирует выполнение бизнес-операций.

- **Use case'ы**: каждый реализует один сценарий использования, наследует `BaseUseCase`
- **Фасады**: `LinkService`, `AdminService` — упрощают интерфейс для веб-слоя
- **DTO**: `ShortLinkResponse`, `BatchCreateResponse`, `UserActivityResponse` — данные для передачи
- **Порты**: абстракции инфраструктуры (`LinkCache`, `RedirectCache`, `StatsCache`, `Logger`, `UnitOfWork`, `HealthCheck`)

### Infrastructure Layer (Слой инфраструктуры)

Реализует порты и обеспечивает техническую поддержку.

- **Repository**: `SQLAlchemyLinkRepository` — преобразование domain ↔ ORM
- **Unit of Work**: `SQLAlchemyUnitOfWork` — управление транзакциями через контекстные менеджеры
- **Кэш**: `RedisLinkCache`, `InMemoryLinkCache`, `NullCache` — двухуровневое кэширование
- **Rate Limiter**: `RedisRateLimiter`, `MemoryRateLimiter` — sliding window алгоритм
- **Авторизация**: `JWTAuthService`, `RBACAuthorizationService` — JWT + RBAC
- **DI Container**: `Container` — ленивое создание и связывание компонентов через component-based архитектуру

### Web Layer (Веб-слой)

Обрабатывает HTTP-запросы и возвращает ответы.

- **Контроллеры**: `ApiController`, `DashboardController`, `AuthController`, `AdminApiController`
- **Middleware**: `AuthenticationMiddleware`, `ErrorHandlerMiddleware`, `RateLimitMiddleware`, `RequestLoggingMiddleware`
- **Декораторы**: `@login_required`, `@require_permission`
- **Схемы**: Pydantic модели для валидации входящих данных

## Безопасность

### Аутентификация

- JWT токены (access + refresh) через `PyJWT`
- Токены содержат `type` claim ("access"/"refresh"); middleware принимает
  **только** access-токен, refresh годится исключительно для `/auth/refresh`
- Деактивация учётной записи отзывает доступ немедленно: `is_active`
  проверяется на каждом запросе, при выдаче access-токена и при входе
- Два способа предъявить токен, по типу клиента:
  - **браузер** — HttpOnly-cookie `access_token` / `refresh_token`
    (`SameSite=Strict`). Иначе никак: страницы дашборда отдаются сервером,
    и обычная навигация не может послать заголовок. Скрипты токен не видят
    и нигде не хранят
  - **программный клиент** — `Authorization: Bearer <token>`. Оба токена
    отдаются в теле ответа `login`, `/auth/refresh` и `/auth/logout`
    принимают `refresh_token` в теле, поэтому cookie-jar не нужен
- Access-токен несёт claim `sid` с именем своей сессии, и оно проверяется
  на каждом запросе. Без этого токен был бы неотзываемым: выход мог бы
  только удалить копию клиента, а любая другая копия работала бы до
  истечения срока
- Срок жизни cookie берётся из `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` и
  `JWT_REFRESH_TOKEN_EXPIRE_DAYS`, то есть cookie и сам JWT истекают вместе
- `COOKIE_SECURE=true` по умолчанию в production
- CORS настроен с явными origins (`CORS_ORIGINS` env var)

### Защита от атак

- **CSRF** — `CsrfProtectionMiddleware`, три проверки вместе на каждом
  небезопасном методе, если запрос аутентифицирован cookie:
  1. **Double submit** — токен лежит в читаемой (не HttpOnly) cookie
     `csrf_token` и дублируется в заголовке `X-CSRF-Token`. Сторонний сайт
     умеет заставить браузер отправить cookie, но не умеет её прочитать и не
     умеет добавить заголовок.
  2. **Подпись** — токен это HMAC-SHA256 на `SECRET_KEY`, привязанный к
     пользователю, которому выдан. Без подписи схема принимает любое
     значение, лишь бы две копии совпали, поэтому тот, кто может выставить
     cookie на домене (XSS на соседнем поддомене, MITM по HTTP), подсадил бы
     известное значение и прошёл проверку.
  3. **Origin** — если браузер назвал origin, он должен быть нашим. Это и
     закрывает подсадку с соседнего поддомена: cookie поддомены не
     различают, `Origin` различает. При отсутствии `Origin` и `Referer`
     проверка пропускается — прокси их вырезают, а подписанный токен всё
     равно обязан сойтись.

  Запрос с **валидным** `Authorization: Bearer` проверку не проходит вовсе —
  клиент, способный выставить заголовок, к CSRF не уязвим, и программные
  клиенты работают без изменений. Освобождение выдаётся по факту того, чем
  запрос аутентифицировался (`g.auth_token_source`), а не по форме
  заголовка, и не действует на эндпоинты из `COOKIE_AUTHORITY_ENDPOINTS`,
  которые читают cookie самостоятельно

- **Кража refresh-токена** — каждый выданный refresh-токен несёт `jti`,
  которому соответствует строка в `refresh_sessions`, и `chain_id` —
  одна цепочка на один вход, сколько бы раз токен ни ротировался.
  Выход отзывает свою сессию и не трогает остальные устройства; блокировка
  аккаунта отзывает все. Обмен токена ротирует его: предъявленный retired,
  выдаётся новый. Повторное предъявление уже потраченного токена означает,
  что он скопирован — отзывается **его цепочка**, а не все сессии
  пользователя, иначе один мёртвый токен позволял бы разлогинить человека
  везде по требованию.
  Захват сессии при ротации — один условный `UPDATE`, а не «прочитать,
  проверить, записать»: иначе два одновременных запроса с одним токеном
  проходят оба и порождают две живые цепочки, при которых вор и владелец
  сосуществуют незамеченными
- **Token type confusion** — JWT содержит `type` claim, `validate_token` проверяет тип
- **X-Forwarded-For spoofing** — `get_client_ip()` проверяет trusted proxies перед доверием к header
- **Rate limit bypass** — rate limiter использует secured `get_client_ip()`

### Авторизация (RBAC)

Четыре роли с иерархией разрешений:

```
┌───────┐     ┌───────┐     ┌──────────┐     ┌───────┐
│ guest │────>│ user  │────>│ analyst  │────>│ admin │
└───────┘     └───────┘     └──────────┘     └───────┘
  регистрация   назначение     назначение
```

| Роль | Описание | Ключевые разрешения |
|------|----------|---------------------|
| guest | Неавторизованный посетитель | `stats:view_basic`, `link:create` |
| user | Зарегистрированный пользователь | `link:create`, `link:view_own`, `link:delete_own` |
| analyst | Аналитик | `stats:view_full`, `stats:view_any`, `link:view_own` |
| admin | Администратор | `admin:all` (все разрешения) |

#### Выдача прав: нельзя дать больше, чем имеешь сам

Каждый путь, которым права попадают к пользователю, проверяет, вправе ли
сам вызывающий их раздавать: назначение ролей, создание пользователя,
создание роли, изменение набора её разрешений. Держатель `admin:all`
проходит свободно — у него есть всё.

*Зачем.* Без этой проверки `admin:manage_users` был коротким написанием
`admin:all`: назначить себе роль `admin` и прочитать разрешения обратно.
`admin:manage_roles` давал то же в два шага — вписать `admin:all` в роль,
которую уже носишь. Обе цепочки укладывались в один HTTP-запрос, то есть
любая «модераторская» роль фактически была полным администратором.

Правило совпадает с отраслевым: Kubernetes проверяет его **в самом
API-сервере** (субъект не может создать Role шире собственной), а
исключения сделаны явными глаголами `escalate` и `bind`, а не подразумеваются;
AWS IAM решает ту же задачу *permissions boundaries* — делегированный
администратор создаёт роли, но не выше выставленного ему потолка. Это та же
конструкция, что `ANONYMOUS_PERMISSION_CEILING`, только на другом конце
шкалы.

*Цена, принятая осознанно:* роль, которая должна раздавать роль `user`,
обязана сама нести все её разрешения. Роль с одним `admin:manage_users`
не сможет назначить `user` — это не дефект, а ровно то, что правило
означает; так же устроено и в Kubernetes.

**Последний администратор не удаляется, не блокируется и не разжалуется.**
Проверка стоит на удалении, деактивации и смене ролей; считается число
активных держателей `admin:all` без учёта того, кого операция касается.
Это про доступность, а не про привилегии: система, потерявшая последнего
админа, восстанавливается только из консоли.

#### Роль `guest` и анонимные запросы

Запрос без аутентификации — не «пользователь без ролей», а роль `guest`.
`RBACAuthorizationService` отвечает на вопросы о нём, читая эту роль из БД.
Поэтому анонимное сокращение ссылок работает не потому, что проверки нет,
а потому что `guest` несёт `link:create`.

Над ролью стоит потолок в коде — `ANONYMOUS_PERMISSION_CEILING` в
`infrastructure/auth/rbac_authorization_service.py`. Что бы ни лежало в
строке `guest`, аноним не получит ничего сверх этого набора.

*Зачем потолок.* Роль читается из БД, то есть её содержимое — состояние
времени выполнения, а до такого состояния можно дотянуться. На штатно
засеянной базе `guest` помечена `is_system: true`, и админский API
отказывается её править (`400 Cannot modify system roles`) — но сам этот
флаг тоже состояние времени выполнения, и остаться без него несложно:
`create_role` жёстко ставит `is_system=False`, а сидирование переписывает
скалярные поля только при `update_existing=True`. Строка `guest`, удалённая
и заново созданная через API, остаётся незащищённой навсегда, и с этого
момента `PUT /api/v1/admin/roles/guest/permissions` пишет в неё что угодно.

Путь узкий. Закрывать его потолком, а не заплаткой на самом пути, стоит
потому, что ошибка этого класса делалась на любом масштабе: в Kubernetes
группа `system:unauthenticated` — обычный субъект RoleBinding, кампания
*RBAC Buster* этим пользовалась, и GKE начиная с 1.28 **запрещает
хардкодом** привязывать `cluster-admin` к `system:anonymous`. Та же история
у PostgreSQL с псевдоролью `PUBLIC` (CVE-2018-1058, дефолт сменили только в
PG 15). Spring Security выдаёт анониму `ROLE_ANONYMOUS` из конфигурации
приложения, изменить её по сети нельзя вовсе.

*Если роли `guest` в БД нет,* аноним не получает ничего. Отсутствие роли
означает «развёртывание не сказало, что можно гостю», а не «можно всё, что
разрешает потолок»: иначе наполовину засеянная база была бы неотличима от
настроенной. На чистой базе роли засеиваются командой
`flask db load-base-roles` — без неё публичное сокращение ссылок не
работает, и это видно сразу.

### Rate Limiting

- Гостевые ссылки: `GUEST_LINK_LIMIT` за `GUEST_LINK_WINDOW_DAYS`
- Auth эндпоинты: защита от brute-force
  - Login: 5 попыток / минуту по IP
  - Register: 3 регистрации / час по IP
  - Refresh: 10 попыток / минуту
  - Logout: 20 попыток / минуту
- API-эндпоинты: настраиваемые лимиты через `RATE_LIMITS` в конфигурации

## Кэширование

Двухуровневая система:

```
┌──────────────────────────────────────────────────────────────────┐
│                         КЭШИРОВАНИЕ                              │
│                                                                  │
│  ┌─────────────────────┐      ┌─────────────────────┐           │
│  │  L1 RedirectCache   │      │  L2 LinkCache       │           │
│  │  short_code →       │      │  short_code →       │           │
│  │  original_url       │      │  Link object        │           │
│  │  TTL: настраивается │      │  TTL: настраивается │           │
│  └──────────┬──────────┘      └──────────┬──────────┘           │
│             │                            │                       │
│  ┌──────────┴────────────────────────────┴──────────┐           │
│  │                                                  │           │
│  │  Запрос редиректа ──> L1 ──> попадание ──> быстрый редирект │
│  │                   │                                │           │
│  │                   └──> промах ──> L2 ──> попадание ──> ответ │
│  │                                  │                           │
│  │                                  └──> промах ──> PostgreSQL  │
│  │                                        │                     │
│  │                                        └──> обновить L2     │
│  │                                              └──> обновить L1│
│  └──────────────────────────────────────────────────────────────┘
│                                                                  │
│  Удаление: Cache.delete(link) очищает все ключи ссылки           │
└──────────────────────────────────────────────────────────────────┘
```

- **L1 (RedirectCache)**: `short_code → original_url` — быстрый редирект (TTL настраивается)
- **L2 (LinkCache)**: `short_code → Link object` — полные данные ссылки (TTL настраивается)

Инвалидация:
- **По TTL**: автоматическая
- **При удалении**: `Cache.delete(link)` очищает все ключи ссылки. Передаётся
  сущность, а не код: запись дедупликации лежит под ключом из хэша и области,
  и одним кодом её не назвать
- **Кэш статистики** сбрасывается при создании и удалении ссылки, а также
  после чистки истёкших. Клики его **не** сбрасывают: они приходят на каждом
  редиректе, и сброс на каждый оставил бы кэшу нечего отдавать — поэтому
  счётчик кликов отстаёт на `CACHE_STATS_TTL`, и это цена, ради которой кэш
  и существует. До этого не сбрасывал вообще ничто, кроме CLI: замерено —
  `/api/v1/stats` отдавал 2 ссылки, когда в БД было 7
- **Обработка ошибок**: ошибки инвалидации логируются, но не прерывают операцию

### Подпись значений кэша

Всё, что кэш хранит, подписано `itsdangerous.TimestampSigner` на
`SECRET_KEY` — той же библиотекой, которой Flask подписывает свои сессии, и
она приходит вместе с ним. Своя реализация HMAC была написана и заменена:
задача давно решена, а у библиотеки есть ровно те два свойства, которые
нужны.

- **Значение непереносимо.** Ключ Redis идёт `salt`-ом, то есть для каждого
  ключа выводится свой ключ подписи. Запись, честно выписанная для одного
  кода, под другим не проверяется — и, в отличие от склейки ключа с
  нагрузкой вручную, границу между ними нельзя сдвинуть.
- **Значение не вечно.** Время выпуска лежит внутри подписанного сообщения,
  а `max_age` при чтении отвергает всё, что старше TTL. Это не дублирование
  TTL Redis: TTL исполняет сервер кэша, и тот, кто может писать в Redis,
  может задать другой — или не задать вовсе. Запись, снятая пока была
  законной, и возвращённая позже, воскрешает то, что описывала: удалённую
  ссылку, снова отдающую редирект, и статистику, замороженную на старом
  числе. Со свежестью внутри подписи срок принадлежит нам, а не серверу
  кэша, и сдвинуть его вперёд владелец байтов не может.

Значение, которое не проверяется, считается промахом — никогда ошибкой:
промах уводит запрос на уровни, которые умеют ответить, а исключение на
пути редиректа было бы 500. Просроченная подпись отвергается тем же
способом, что и поддельная: обе означают «это не ответ».

*Зачем.* Раньше значение бралось дословно. Одной команды
`SET link_shortener:code:<code> '<валидный JSON>'` хватало, чтобы редирект
увёл на чужой адрес; тем же способом подставлялись запись дедупликации и
статистика — последняя публиковалась как факт, вместе с чужими
`original_url` для держателя `stats:view_full`.

*Смена `SECRET_KEY`* делает весь кэш непроверяемым — то есть развёртывание
просто прогревает его заново. Записи, оставшиеся от сборки без подписи,
ведут себя так же. Каждый отказ пишется в лог: это либо посторонняя запись
в Redis, либо смена ключа, и оператору стоит знать о том и о другом.

## Транзакционность

Паттерн Unit of Work:

```python
with self.uow_factory() as uow:
    link = uow.links.find_by_code(code)
    link.increment_clicks()
    uow.links.save(link)
    uow.commit()  # Явный коммит
# При выходе из контекста без коммита — автоматический rollback
```

## Логирование

Три уровня:

1. **Application Logger** — бизнес-события (создание, редирект, ошибки)
2. **Audit Logger** — аудит безопасности (создание, удаление, доступ)
3. **Failover** — автоматическое переключение при недоступности основного логгера

## Расширяемость

### Добавление нового use case

1. Создать `application/use_cases/<domain>/<name>.py`
2. Наследовать `BaseUseCase`, объявить зависимости как поля `@dataclass`
3. Реализовать метод `execute()`
4. Зарегистрировать в DI-контейнере (`infrastructure/di/components/use_cases/`)
5. Добавить геттер в `infrastructure/di/container.py`
6. Подключить к контроллеру или фасаду

### Добавление нового эндпоинта

1. Добавить метод в контроллер
2. При необходимости создать Pydantic-схему в `web/schemas/`
3. Добавить route в `_register_routes()`
4. При необходимости добавить декораторы авторизации

### Добавление новой роли

1. Определить разрешения в `domain/system_permissions.py`
2. Добавить роль в seed data
3. Выполнить `flask db load-base-roles`
